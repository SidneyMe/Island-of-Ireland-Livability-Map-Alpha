# План: завершить v4 и выпустить публичную карту

Дата аудита: 2026-10-26. Статус обновлён 2026-10-27: самостоятельная публикация v4 и безопасный verifier опубликованной сборки реализованы; остальные этапы остаются планом.

## Цель и принятые допущения

Первый релиз — карта с текущими функциями и моделью `daily-access-v4`, Python API и PostGIS на Linux VPS. Бюджет инфраструктуры — €20–30/месяц. Сначала завершаем v4, затем готовим деплой.

Рабочие допущения: сохраняем текущие категории, веса и кривые v4; тяжёлые расчёты выполняем на локальном ПК; обновления сначала запускаем вручную после проверки. Новые категории, автоматический еженедельный релиз и отдельное статическое демо остаются следующими задачами.

## Выполнено 2026-10-27: самостоятельная публикация v4

- [x] POI, transport reality, service deserts и summary подготавливаются из текущих источников без v3-сборки и без глобального `_STATE` в общей подготовке.
- [x] Снимок GTFS, дата и окна сохраняются в контексте; формулы, веса и классификация scoring v4 не менялись. Существующие display-категории/фильтры POI сохранены.
- [x] В публикационном ключе учтены версия отображаемых слоёв и noise artifact. Поля происхождения/количеств формируются заново; повторная публикация не удаляет активные строки.
- [x] Шум копируется из подготовленного artifact общими SQL helpers и выпекается отдельно. Full требует accurate; dev/test могут явно отключить отсутствующий artifact. Сырые архивы не читаются.
- [x] Проверены целевые Python-регрессии и frontend suite; отдельная интеграция создаёт временную PostGIS-БД, применяет канонические миграции и проверяет profile test на небольшой фикстуре: CLI из кэша, SQL, PMTiles/MVT слои, stale v3, повтор, отказ bake, подготовленный noise и API/inspect. Рабочая БД не меняется.

Это завершение первого подпункта, а не всей проверки качества v4. Национальный full-прогон, аудит parks/coverage, переносимый пакет и атомарный деплой остаются впереди.

## Выполнено 2026-10-27: verifier опубликованной v4-сборки

- [x] `daily_access_verify_shards.py` выбирает конкретный опубликованный `build_key` (`--build-key` либо последнюю завершённую v4-сборку профиля), читает закреплённые OSM/GTFS/Overture fingerprints и не вызывает обновление transit reality.
- [x] Национальная выборка больше не материализует десятки миллионов Python tuples: число валидных ячеек считается по одному шарду, квоты воспроизводимы по `--seed`, а в памяти одновременно держится индекс только одного шарда плюс результат выборки. При достаточном размере выборки покрывается каждый непустой шард.
- [x] Общая проверка surface сверяет полный inventory shell/score, ключи и связь tiers, checksums, обязательные поля, размерности массивов и координаты shard origin. Её используют publish gate и runtime readiness; повреждённый shard теперь делает `inspect_ready=false`.
- [x] Reach cache хранит полный рекурсивный inventory и checksums для `.npy`, JSON и `objects/*.bin`; проверяются обязательные файлы, связи ключей, dtype/shape массивов, число origins/objects и структурные размеры бинарников. Повреждённый reach запрещает reuse, verify и publish. Формат поднят до `reach_cache_version=3`; это перестраивает reach/score, но не дорогой geometry-only shell.
- [x] Публикуемая summary сохраняет пути и fingerprints, нужные для воспроизводимой проверки. `DISPLAY_LAYERS_VERSION` увеличена до 2, поэтому старая публикация не переиспользует прежний build key; legacy v4 без pinned identity verifier просит перепубликовать.
- [x] Регрессии: расширенный v4-набор — 130 тестов; отдельно прошли 85 config/hash тестов и end-to-end публикационная интеграция в одноразовой PostGIS-БД. Национальный verifier на реальных данных ещё не запускался.

## Что было подтверждено аудитом 2026-10-26

- Есть Python reference, Rust-реализация, шардированный расчёт 50 м, API inspect, PNG-каналы и публикация v4 в PostGIS/PMTiles. Переписывать расчёт с нуля не требуется.
- В локальных манифестах есть завершённые `test` и национальный `dev` от 2026-10-23. У национального `dev` — 269 шардов и примерно 33,5 млн ячеек суши. Завершённый актуальный `full` аудитом не подтверждён.
- У `dev` около 8,92 млн ячеек без пешей сети; средний total среди ячеек со статусом `ok` — 4,418. Карта репозитория также фиксирует около 48% непривязанных зелёных объектов. Это основания для проверки, а не доказанные ошибки модели.
- **Исправлено 2026-10-27:** ранее `publish_daily_access` копировал POI, транспорт, service deserts и часть метаданных из подходящей v3-сборки; теперь источники подготавливаются самостоятельно.
- Идентичность runtime зависит от локальных путей/метаданных исходников; пути shell/score записываются в БД как пути машины сборки. Копирование Windows-сборки на Linux само по себе недостаточно.
- **Исправлено 2026-10-27:** runtime и publish сверяют полный inventory shell/score, checksums и размерности; повреждённый shard даёт `inspect_ready=false`.
- Публикация сначала переключает записи БД, потом заменяет общий PMTiles-файл. Повторная публикация того же build key исправлена 2026-10-27: активные строки переиспользуются, копирования point layers из v3 больше нет. Атомарность переключения БД и файлов пока не реализована.
- `serve --deployment` проверяет basemap и наличие основных файлов, но не является полной проверкой готовности публичного релиза. Есть `ThreadingHTTPServer`; отсутствуют отдельный production runbook, health/readiness endpoints и готовый деплой приложения.
- `setup.sh` и scheduled refresh пока запускают v3 `precompute`; workflow не доставляет проверенный v4-релиз на хостинг.
- Проверка: frontend suite прошёл; из 96 целевых Python-тестов v4 94 прошли, 2 PostGIS-теста пропущены. Rust/Python parity и синтетический shell→reach→score тест выполнялись. Первый запуск в песочнице имел ошибки доступа TemporaryDirectory; повтор вне песочницы прошёл. Полный Rust suite, реальные PostGIS-тесты и full-сборка в этом аудите не выполнялись.

## 1. Завершить v4 — обязательный первый этап

### Полнота данных и качество результатов

- [x] Подготовка отображаемых POI, transport reality, service deserts и summary самостоятельна; предварительный расчёт v3 не требуется. Реализовано 2026-10-27, см. статус выше.
- Для национального релиза проверять оба GTFS feed, даты покрытия analysis window, доступные остановки и потери привязки отдельно для ROI и NI. Не использовать `--allow-missing-transport` в публичном релизе. Шум остаётся отдельным отображаемым слоем и не влияет на score.
- Разобрать причины потерь green: закрытый доступ, отсутствие входа/пешеходного ребра, неполные исходные данные и ошибка привязки. Проверить ручную выборку городских, сельских и крупных парков; исправлять подтверждённые ошибки, не ослаблять правила доступа ради красивой статистики.
- Проверить распределение total и компонентов, а также статусы сети на контрольных точках Dublin, Belfast, Cork, Derry, Galway, в пригородах, сельской местности и у побережья. Сопоставить низкие значения с фактическими расстояниями и классификацией объектов.
- Сохранить текущую main-island маску; показать её границу покрытия в объяснении карты. Achill и Great Island/Cobh сейчас вне этой маски. Расширение географии — отдельное изменение модели.

### Сборка и проверка

- [x] Исправить национальный verifier: выбирать воспроизводимую выборку по шардам без списка всех миллионов ячеек в памяти. Проверка использует конкретный опубликованный build и pinned inputs, не обновляет transit reality. Реализовано 2026-10-27; реальный национальный прогон остаётся ниже.
- [x] Проверять полный список шардов, ключи shell/reach/score, обязательные версии и поля, checksum, размерности и совместимость tiers. Shell/score и reach inventory реализованы 2026-10-27; старый reach cache без inventory автоматически не переиспользуется.
- Полную проверку выполнять при подготовке/загрузке релиза, а не хешировать все данные на каждом HTTP-запросе. Readiness использовать результат проверки неизменяемого пакета.
- Прогнать PostGIS green/approach тесты в изолированной тестовой БД и Rust tests. Затем собрать `full`: fine vector PMTiles, PNG-каналы, basemap, noise и остальные слои. Замерить время, RAM и размер результата.
- Добавить регрессии: v4 с нуля без v3-сборки; повреждённый/отсутствующий shard запрещает readiness; повторная публикация безопасна; ошибка bake/rename/перезапуск не повреждают последний хороший релиз.

Результат этапа: полноценный v4 `full`, проверенный на реальных данных и в браузере; отчёт о качестве и ресурсах, понятные ограничения покрытия. До этого этапа публичный релиз не готов.

## 2. Сделать переносимый и воспроизводимый релиз

- Ввести пакет с `release.json`: версия формата, release id, commit, build key, версия модели, профиль, даты и fingerprints источников, относительные пути файлов и их SHA-256, версия схемы БД, результаты проверок. Не включать секреты.
- Добавить отдельные операции подготовки пакета, проверки и активации. Подготовка и загрузка кандидата не меняют активный релиз; одинаковый готовый релиз допускает безопасный повторный запуск.
- Runtime запускать с явным release manifest/build key. В этом режиме не вычислять идентичность по файлам OSM/GTFS/границ на VPS; пути артефактов разрешать относительно корня пакета. Сохранить прежний локальный запуск для разработки.
- В пакет включать frontend, локальные glyphs/sprites, basemap/livability/noise PMTiles, shell/score shards, manifest и transport export. Для БД переносить только необходимые опубликованные строки выбранного build и совместимую схему; не копировать raw OSM/GTFS/noise, граф и reach-cache без runtime-потребности.
- Опубликовать файлы по неизменяемым URL с release id. API inspect и surface-запросы привязать к ожидаемому build key; несовпадение возвращает 409, интерфейс обновляет runtime перед повтором запроса. Старый PMTiles URL никогда не должен начать отдавать байты нового архива.
- Исправить staging/publish так, чтобы не удалять активную сборку при повторе. Хранить последние три исправных релиза. Переключать кандидата только после проверки его БД и файлов; откат возвращает согласованные код, manifest и данные.

Результат этапа: пакет, собранный на Windows, запускается в чистой Linux-среде без исходных датасетов; публикация и откат воспроизводимы.

## 3. Подготовить сервер и frontend к публичному доступу

- Сохранить текущий runtime и библиотеки; не добавлять зависимости и не переписывать приложение на другой framework в этой задаче.
- Поставить Nginx перед Python: HTTPS, статические файлы/PMTiles напрямую, корректные HEAD/Range/206/416/ETag, API через loopback. Не публиковать Python-порт и PostgreSQL наружу. Для PMTiles отключить внешнюю компрессию, меняющую byte offsets.
- Ограничить конкуренцию дорогих API/PNG-запросов, таймауты и очередь; при перегрузке возвращать контролируемый 503. Настроить ограничение запросов в Nginx и неограниченный рост PNG-кэша заменить лимитом/очисткой. Не ставить низкий общий лимит на обычные tile-запросы карты.
- Разделить установку/миграции и runtime: схема готовится отдельной операцией с write-ролью, HTTP-процесс получает read-only доступ. Startup проверяет совместимость схемы вместо автоматического DDL/Alembic.
- Добавить `/healthz` для живого процесса и `/readyz` для согласованного v4-релиза. Readiness проверяет доступность БД, выбранный build и проверенные файлы; сбой даёт 503. В диагностике не раскрывать пароли и локальные пути.
- Для HTML и runtime metadata использовать повторную проверку/`no-store`, для неизменяемых release assets — долгий cache. В cache key PNG учитывать build, разрешение и канал.
- В интерфейсе показать дату данных, смысл v4 и coverage; корректно обрабатывать загрузку, API 503, смену build и отсутствие данных. Старые counts/clusters/effective units остаются недоступными, а не подменяются нулями. Проверить переключение всех score-каналов и мобильный экран.
- Сохранить attribution; подготовить короткое объяснение методики и privacy. Не логировать координаты inspect, query string и IP пользователей; технические метрики — route/status/duration без персональных данных.

Текущий `http.server` не следует выставлять непосредственно в интернет: Python отдельно предупреждает о его ограничениях для production. Для первой beta сохраняем его только за Nginx с указанными ограничениями и обязательным нагрузочным тестом; если тест не проходит, публикация блокируется.

## 4. Деплой и проверка перед публикацией

- Linux x86-64, Ubuntu 24.04 LTS; Nginx, systemd, отдельный непривилегированный пользователь приложения, локальный PostgreSQL/PostGIS. Docker и Rust на runtime-хосте не требуются при доставке готовых артефактов.
- Начальная цель для измерений — 4 vCPU, 8 GiB RAM. Диск выбирать по фактическому full-пакету: место для трёх релизов, runtime-БД, ограниченного tile-кэша и минимум 25% свободного пространства. Бюджет включает VPS, адрес, резервное хранение и налоги; домен учесть отдельно. Конкретный тариф выбирать после замера full, не покупать по оценке dev.
- Добавить шаблоны Nginx/systemd/env и команды upload/validate/activate/rollback. Кандидата проверять на отдельном локальном порту до переключения Nginx; после переключения повторять smoke. При неуспехе возвращать предыдущий backend и данные.
- На staging пройти реальный сценарий: открыть карту, масштабировать до 50 м, переключить четыре компонента и total, открыть popup, включить noise/landuse/transport/service deserts, скачать export, проверить glyphs/sprites и мобильный браузер.
- Проверить HTTP: частичный PMTiles ответ действительно 206 и нужные байты; неверный диапазон 416; HEAD без тела; API/PMTiles относятся к одному build; недостающие файлы блокируют активацию; смена релиза в открытой вкладке не смешивает scores.
- Начальный нагрузочный критерий beta: 20 параллельных inspect-запросов и 4 параллельных PNG-запроса в течение 10 минут, без 5xx при штатной нагрузке, без роста RSS после прогрева, тёплый inspect p95 ≤500 мс и PNG p95 ≤1 с. Отдельно замерить холодные запросы; при перегрузке допустим контролируемый 503. Статическую раздачу проверять отдельно от API.
- Добавить Linux CI для v4 unit/parity и fixture runtime, сборки frontend и проверки переноса пакета. Реальные национальные данные проверяются в release job, а не на каждом PR.
- Scheduled refresh доработать после первого успешного ручного обновления: сейчас он строит v3. Пока он не умеет собирать и проверять v4, не направлять его результат на публичную карту.
- Настроить внешний readiness-check и уведомления о недоступности, место на диске, ротацию технических логов, резервную копию опубликованной БД/manifest и пробный restore/rollback. При провале обновления последний хороший релиз продолжает работать.

Порядок работ: **качество и полнота v4 → full-сборка → переносимый пакет → runtime/Nginx → staging и откат → публичный домен → первое ручное обновление**.
